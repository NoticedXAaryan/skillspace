# SkillSpace Deep Audit & Rewire Plan

## Product Manager Assessment

**What SkillSpace claims to be:** "npm for AI skills" — install, share, version, and execute AI capabilities across models.

**What it actually is today:** A monorepo with well-structured code that doesn't work end-to-end. The CLI talks to a registry that requires a running PostgreSQL. The web UI has mocked flows. The auth between CLI and registry is mismatched. A user cannot go from "I found this project" to "I installed and ran a skill" without hitting walls.

**The gap:** The architecture is solid (v2 schema, adapter pattern, BetterAuth). The code quality is decent. But nothing is *wired together* properly. It's a collection of well-written parts that don't form a working whole.

---

## Critical Findings (What's Actually Broken)

### 1. Auth Mismatch Between CLI and Registry (P0)
- **CLI** sends `Authorization: Bearer <token>` header (api.ts:40)
- **Registry** uses BetterAuth session cookies via `getUserFromRequest()` (auth.ts)
- BetterAuth's `/api/auth/sign-in/email` returns a token in JSON, but the registry API expects session cookies
- **Result:** `air login` saves a token, but `air publish` and `air whoami` fail because the registry doesn't read Bearer tokens
- **Fix:** Either make registry accept Bearer tokens OR make CLI use session cookies. Bearer is simpler for CLI.

### 2. Create Page is Fully Mocked (P0)
- `apps/registry/src/app/create/page.tsx` line 42: `setTimeout(() => { confetti(...); toast.success(...) }, 1500)`
- Never calls `POST /api/packages`
- Uses `localStorage.getItem('skillspace_token')` for onboarding (wrong — should use session)
- **Fix:** Wire up to real `POST /api/packages` with proper auth

### 3. Playground is Frontend-Only (P0)
- `PlaygroundClient.tsx` uses `<AIChat>` component that appears to be a mock
- No actual API call to execute skills
- **Fix:** Either connect to a real execution endpoint or clearly mark as "coming soon"

### 4. Packages Listing API Mismatch (P1)
- Client sends `offset` parameter (packages/page.tsx:58)
- API expects `page` parameter (api/packages/route.ts:18)
- Client sends `search` parameter (packages/page.tsx:59)
- API has no `search` filter — only `type` and `sort`
- **Result:** Pagination is broken, search doesn't work on listing page

### 5. No Seed Data in Database (P1)
- Landing page shows example skills as static HTML when DB is empty
- But `/packages` page shows "The registry is empty" with no examples
- No seed script to populate the database
- **Fix:** Create a seed script that inserts the 10 example skills

### 6. Missing .env.example (P1)
- No documentation of required environment variables
- Developers can't set up the project without reading source code

### 7. Dockerfile Not Standalone (P2)
- `next.config.ts` doesn't have `output: 'standalone'`
- Docker build won't work for production

## What Makes This Revolutionary (Not Just Another Tool)

The user's vision, distilled:

1. **Cross-system persistent memory** — Skills and context that survive switching between Claude Code, Cursor, and this app. The memory-mcp package is the seed; needs to be portable across editors.

2. **One-line tool installation** — `air install graphi` should install a project graphing tool. The registry + CLI is the delivery mechanism. The skill.yaml is the contract.

3. **Sandboxed execution** — Skills declare permissions, runtime enforces them. FileSystemSandbox and NetworkSandbox exist in code; need CLI integration.

4. **Agent connectivity** — Skills should work with any AI agent. The adapter pattern (Claude, OpenAI, Gemini, Ollama) is the foundation.

5. **Developer-first UX** — No mobile. Snappy. Dark theme. Code-first. Like Docker Hub meets npm meets Homebrew.

## Deep Feature Analysis

### 1. Persistent Cross-Tool Memory (The Killer Feature)

**User's ask:** "Even if I am hopping between different applications, this tool should help me remember the context of everything."

**Current state:** `packages/memory-mcp` has SQLite FTS5 memory with `save_memory` and `search_memory` tools. It works locally but doesn't sync.

**What needs to be built:**

```
┌──────────────┐     MCP Protocol     ┌──────────────┐
│  Claude Code  │ ◄────────────────── │  Memory MCP  │
│  Cursor       │                     │  Server      │
│  SkillSpace   │                     │  (stdio)     │
│  Any AI tool  │                     └──────┬───────┘
└──────────────┘                            │
                                            │ sync
                                    ┌───────▼───────┐
                                    │  Local SQLite  │
                                    │  ~/.skillspace/ │
                                    │  memory.db     │
                                    └───────┬───────┘
                                            │ push/pull
                                    ┌───────▼───────┐
                                    │  Registry API  │
                                    │  /api/memory   │
                                    └───────────────┘
```

**Implementation steps:**
1. Add `memory.db` path to `~/.skillspace/` config
2. Add `air memory push` — uploads local memories to registry
3. Add `air memory pull` — downloads registry memories to local
4. Add `air memory sync` — bidirectional sync with conflict resolution
5. Add `/api/memory` endpoints to registry (CRUD + search)
6. Memory MCP server reads from local SQLite, syncs to cloud when available
7. Any AI tool configured with the MCP server gets the same memory

**Key design decision:** Memory entries have a `source` field (which tool created them) and a `hash` for deduplication. Sync merges by hash, not by timestamp.

### 2. Sandboxing (Security Layer)

**User's ask:** "AI could obviously delete my whole system if he wants but sandbox and red lines would actually protect him."

**Current state:** `FileSystemSandbox` and `NetworkSandbox` exist in `packages/runtime/src/sandbox.ts`. They're implemented but not wired into the CLI.

**What needs to be built:**

```
air run security-review --input ./src
    │
    ├── Load skill.yaml → get declared permissions
    │   permissions: [filesystem.read]
    │
    ├── Create sandbox with declared permissions
    │   FileSystemSandbox: read-only access to CWD
    │   NetworkSandbox: no access
    │
    ├── Execute skill within sandbox
    │   ├── Skill tries to read file → ALLOWED (declared)
    │   ├── Skill tries to write file → BLOCKED (not declared)
    │   └── Skill tries to make HTTP request → BLOCKED (not declared)
    │
    └── Return result + audit log
```

**Implementation steps:**
1. In `apps/cli/src/commands/run.ts`: after resolving skill, create sandbox from permissions
2. Pass sandbox to `Executor.run()` as a context option
3. In `packages/runtime/src/executor.ts`: use sandbox for all filesystem/network operations
4. Add permission prompt for borderline cases (e.g., skill requests `filesystem.read` but tries to read outside CWD)
5. Log all sandbox violations to `~/.skillspace/audit.log`

### 3. MCP Integration (Agent Connectivity)

**User's ask:** "How can I connect my agent with every single CLI tool I want?"

**Current state:** `McpManager` in `packages/runtime/src/mcp.ts` can install, start, stop MCP servers. `McpRegistry` handles connections. But `air mcp install` doesn't fully work.

**What needs to work:**
```
air mcp install github          # Installs GitHub MCP server
air mcp install filesystem      # Installs filesystem MCP server
air mcp list                    # Shows installed MCP servers
air run my-agent                # Agent uses installed MCPs
```

**The agent.yaml already declares MCPs:**
```yaml
mcps:
  - name: "@modelcontextprotocol/server-github"
    transport: stdio
    config:
      token: "$GITHUB_TOKEN"
```

**What's missing:**
1. `air mcp install` needs to actually download and configure the MCP server
2. The MCP registry needs to map names to actual npm packages
3. When an agent runs, its declared MCPs need to be started and connected
4. The agent executor needs to route tool calls to the correct MCP server

### 4. Graphy Integration (Example of One-Line Install)

**User's ask:** "I want cool stuff like graphy to be installed in a single line like `air install graphy`"

**This is the proof of concept for the whole product.** The flow should be:
1. User runs `air install @skillspace/graphy`
2. CLI downloads the skill package from registry
3. Package contains `skill.yaml` + any MCP server code
4. `air run graphy --input ./src` executes the skill
5. Skill uses its MCP server to analyze the project
6. Returns a project graph/visualization

**To make this work, we need:**
1. The registry to have packages (seed it)
2. The install flow to work end-to-end (fix auth)
3. The run flow to execute skills (fix executor)
4. Skills to be able to declare and use MCP servers (fix MCP integration)

## Vercel/Expo-Style Architecture Redesign

### The Vision

Inspired by Vercel, Expo, and similar platforms. The key insight: **the registry doesn't store code — it stores metadata and links to GitHub.**

```
Current:  CLI → uploads .skillpkg → Registry stores in S3 → CLI downloads from S3
Proposed: CLI → links GitHub repo → Registry stores metadata → Users clone from GitHub
```

### How It Works (User Flow)

**Step 1: Sign Up / Sign In**
- User visits skill-space.dev → clicks "Sign Up" → GitHub OAuth
- Redirected to dashboard (like Vercel after deploy)

**Step 2: Create Package (Web or CLI)**
- **Web:** Dashboard → "New Package" → fill form → link GitHub repo → publish
- **CLI:** `air init` → create skill.yaml → `air publish` → links to GitHub

**Step 3: Configure API Keys**
- Dashboard → Settings → API Keys → add OpenAI/Anthropic/Gemini keys
- Keys stored encrypted, used for playground execution

**Step 4: Test in Playground**
- Dashboard → Playground → select skill → type input → see real execution
- Uses the user's configured API keys

**Step 5: Publish to Public**
- Package is verified (linked to public GitHub repo)
- Appears in registry with "Verified" badge
- Others can install: `air install @username/skill-name`

```prisma
model PackageVersion {

}
```

**New: UserSettings table:**
```prisma
model UserSettings {
  id             String   @id @default(cuid())
  userId         String   @unique
  openaiKey      String?  // encrypted
  anthropicKey   String?  // encrypted
  googleKey      String?  // encrypted
  ollamaUrl      String?
  defaultModel   String?
}
```
